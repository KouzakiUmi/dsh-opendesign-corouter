# OpenDesign CoRouter plugin

## Purpose and acceptance

This package connects OpenDesign CoRouter to DSH with separate Design Plan and paid-model providers. Its settings page is an operational configuration surface, not a static catalog.

Required behavior:
- Settings controls show pending values immediately and roll back rejected saves. Serialize configuration writes, track every pending field, and distinguish namespace readiness from transport writability. Load local status independently of quota reads; background quota refresh must not hold a saved control disabled.
- Configuration schemas survive the Host's `volatileForm` projection and repeated JSON rehydration. Transform callbacks keep a self-contained JSON serializer after every reconstruction; the browser fixture consumes the real Host-projected schema. Configuration and Remote field limits agree.
- Settings prioritize actionable connection status and controls; model parameters and explanatory details are progressively disclosed. Disabled controls explain loading, unavailable, or read-only state. Explicit model output edits must fit the effective context budget; the inherited catalog maximum is not the actual default reservation. Resolved context metadata reports the full combined window; the Host reserves output capacity. Catalog context values follow [model context evidence](docs/model-context.md); a gateway-reported smaller window may lower the reference, user overrides win, and neither is a verified CoRouter limit. Discovery does not replace the catalog's output-capacity field with gateway budgets; the automatic output reservation may change with the context window.
- The context window is chosen as one of three mutually exclusive tiers: default 272000, extended 500000, maximum 872000. Each tier is a combined input-plus-output working window, not an input budget. The catalog's vendor reference stays the known reference: it caps tier availability, remains the evidence value, and is never rewritten to a tier number. The effective working window is the smaller of the selected tier and the known reference; a tier above the reference is not selectable, and the default tier is clamped to the reference. Output stays reserved inside that window: the automatic reservation is at most one quarter of the total window and never exceeds the model's output cap. The selected tier is stored as `ModelSettings.contextTier` (`default` / `extended` / `maximum`); `contextWindow` and `contextTier` are never both set. Any legacy `ModelSettings.contextWindow` number is read as-is, stays uncapped by the reference, and is shown as a custom state — a value that happens to equal a tier's token count is still a custom window, never a tier. Choosing a tier clears the numeric override atomically: `extended` and `maximum` store the tier id, `default` removes both fields. Reset returns to the default tier, not to the vendor maximum. A tier that conflicts with an explicit `maxTokens` is rejected so the user clears or lowers the output first; explicit values are never rewritten silently. Tiers move the local working budget only and do not widen server or gateway limits.
- The chat view carries a context quick control next to the model selector. It appears only when the session's selected model belongs to one of this plugin's two providers, it follows the session's own model directory rather than any global "last used" model, and it shows that model's effective total window. Its popover offers the same three tiers and writes the same global model default as the settings page: it is not a session override, other sessions using that model see the change, and requests that were already prepared keep their snapshot. Both entry points write through one coordinator that serializes configuration writes, locks a pending field in both surfaces, and rebases the model-settings diff onto the host's current map, so concurrent changes to other models or to other fields of the same model survive. Switching the model closes the popover, and a late result from the previous model is never written to the new one. Legacy numeric windows, reference clamping, explicit-output conflicts that keep the original value, and the pending/rollback rules behave the same in both surfaces.
- Settings use DSH semantic colors, including explicit native select option colors and a host-theme-aligned color scheme, even when the operating system uses the opposite scheme. Check enabled text and dropdown options in light, dark and forced-color modes.
- Layout adapts to the available settings-pane width as well as the viewport. Model groups size independently, and secondary labels and model actions remain readable and usable in a narrow pane.
- Quota refresh, window recovery and subscription end show relative time with their exact timestamps accessible separately; countdowns track the actual scheduled instant, stop with the UI, and never imply an unknown refresh or recovery.
- Model settings show the official website's public input/output and cache price tiers by exact model ID, separately from gateway discovery and account entitlements. Fetch on first opening the model page and on explicit refresh, without credentials; preserve the last successful snapshot with a stale warning on failure, and never infer missing prices or merge different tiers or units.
- Quota displays Design Plan windows, subscription credits, recharge credits, and total balance as distinct amounts. Each compact window shows remaining percentage, remaining-capacity bar, labelled used/total credits and its own recovery row. The service-reported remaining credits, window start and reset mode stay in collapsed details; source and update time are separate labelled rows. A status banner and progress colors reflect the most constrained known window only when its reading is current and complete, with an explicit neutral or warning state for missing, stale, partial or expired data. Window resets, subscription period end, and the next local refresh are different timestamps. Missing values remain unknown.
- Desktop authentication is tried first when enabled. A complete saved console session may replace a partial desktop result as one whole snapshot; account data is never combined across identities.
- Independent login uses bounded device authorization. A login started from settings automatically requests the approval window once after entering the waiting state; failed opens remain visible and can be retried manually without polling reopening windows. The Host may show the approval page in one short-lived Chrome window it launches itself through `playwright-core`; it never creates, drives or reads the user's own browser profile, and the ordinary official link stays available as the manual path. Activation links accept only the official page with a legacy code or the public `deviceId`/`userCode` pair; the Host binds both pair values to the authorization response, rejects extra or duplicate fields, and never exposes the polling secret. Only waiting-state public code/link/expiry reach the UI, and the opener reports a fixed code, never a URL or browser handle. An explicit pending poll with only null or absent token fields remains waiting and does not close the approval window; partial keys, unknown states and failures remain errors. Store both issued keys atomically; preserve commit/cancel ordering and read compatibility for legacy Cookie grants.
- Login/cancel/API-key action responses update the Client immediately and supersede older reads. The approval panel has a clipboard action plus a selectable-link fallback; copy feedback is scoped to its job. Quota cache invalidation produces an unread snapshot, while `need-login` is reserved for an observed missing/expired session.
- `Status.apiKeySource` optionally reports `reference`, `stored`, or `device` without credential values. Settings show the effective source and explain when an ambient reference outranks a newly saved Key. Explicit credential references and manually saved API keys outrank device runtime tokens. Device tokens are bound to the prepared request’s official origin, not mutable current configuration. Device quota never uses desktop CLI data; only explicitly personal workspaces may read account billing summaries.
- The profile names a credential reference only when the user sets one; `apiKeyEnv` has no schema default and requests fall back to `COROUTER_API_KEY` inside the plugin. The Host model page joins the profile's effective value (`apiKeyEnvOf`) and reports whatever it finds there, so a schema default claimed a reference on every install and marked both channels as missing an API key. The fix is to leave the profile unnamed, not to make the reference look configured: with nothing named the page treats both routes as authenticated — no key warning, no forced setup card, and no first-run prompt from these rows; that readiness flag is joined across every row, so no other provider's setup card appears either while this plugin is installed — while the plugin's own settings page stays the surface for saving a key, naming a reference or signing in. `Status.config.apiKeyEnv` travels as an empty string when the profile names nothing, so the settings field stays blank with the default as its placeholder instead of pre-filling a name that a save would then persist. Both channels also declare `nativeAuth: { env: [], oauth: true }`, which describes how they authenticate; the observed page build only acts on that declaration for its own DeepSeek and pi-ai layouts and shows this namespace a read-only hint, so it is a description rather than the mechanism behind the missing-key fix. `COROUTER_API_KEY` authenticates through the credential seam's environment fallback rather than a per-route env field.
- Catalog group semantics: official Core / Design Plan means included models; official Plan means paid plan models. Preserve the historical `opendesign-corouter-plan` Provider ID for the included channel and `opendesign-corouter-paid` for the paid channel. The catalog has 39 entries (13 included-channel, 26 paid-channel): the public Core list contains 12, and per-model service preflight also confirmed MiniMax M3.1 Flash coverage in the observed workspace. Treat this as scoped evidence, not a universal entitlement guarantee. See [model evidence](docs/client-evidence.md) and the maintenance procedure below.
- A fetched model catalog is published to the selector as one update; selector notification failure restores the prior catalog and reports that stage separately, allowing a later refresh to recover.
- Each model can be enabled or disabled and given explicit generation defaults. Disabling affects both advertised models and direct invocation. Settings are persisted through the host configuration service.
- Image input capabilities follow [model evidence](docs/model-capabilities.md), with a per-model enable/disable override and a way to restore the catalog default. List, discovery, resolved metadata and actual requests use the same effective override. Unknown remains unknown in metadata and attempts to forward readable images instead of claiming the model is text-only; explicit text-only projects images to placeholders. The model row uses a compact image control while temperature and other advanced parameters remain collapsed by default. Within each settings group, enabled models appear before disabled models, with stable catalog order within each state; pending changes, rollback, search and pagination follow that ordering.
- Inference supports Chat Completions, Responses, and Messages. Model discovery always uses the configured gateway's OpenAI-compatible `GET /models` endpoint, independently of inference protocol selection. User-facing refresh/source messages say “刷新模型目录” / “当前网关”; protocol compatibility must not imply the models come from OpenAI's own service. A successful read is saved as the plugin's validated `modelCatalog` snapshot: the same gateway restores it after a Host restart instead of falling back to the built-in list, a different gateway ignores it, and a failed settings write keeps the live catalog with an explicit unsaved warning. One settings write rewrites the composed profile and may rebuild the plugin tree, so only a `SETTINGS_CONFLICT` revision conflict is retried (once, after re-reading the revision); any other failure is reported immediately instead of repeating a write that can only fail the same way.
- Inline image request size is bounded independently of token context, including for compaction summaries. Over-budget images and HTTP 413 with retained inline images use the Host's durable image-offload recovery; older occurrences become placeholders without deleting attachments. A 413 without images stays a request-size error, not a token-window overflow. The image budget is adjustable, and recovery requires the Host image-offload plugin.
- Messages preserves native signed and redacted Claude thinking as opaque replay metadata aligned with assistant blocks, including empty thinking; replay only unmodified data from the same provider, model, gateway and credential identity. A plugin-owned random binding secret is persisted by the credential service; without that service the identity binding is instance-local. Never expose opaque data as reasoning text, revive dropped blocks, or replay it across protocols or identities. For the eight documented Claude IDs, the 2023-06-01 Messages compatibility API permits at most one sampling field at its default (temperature 1 or top-p 0.99) and a synchronous output cap of 128000; reject incompatible settings before credential/network I/O and keep saved overrides clearable. Other protocols retain their own semantics.
- Reasoning choices follow the [model evidence](docs/reasoning-evidence.md) and are intersected with the active protocol in Host metadata, settings and request validation. The model settings show the current default with an explicit edit, save and cancel flow; drafts do not persist until saved, rejected saves preserve the draft, and concurrent external changes remain visible alongside any save error. Defaults never create a capability list. Stale defaults remain clearable, do not corrupt model metadata, and fail before credential/network I/O when used. Vendor defaults remain upstream-owned.
- The monitor applies only to `deepseek-v4.1-flash` on this plugin's plan provider (`opendesign-corouter-plan`) with tools enabled; the paid provider, identically named models under other providers, and other models of the same provider are never reviewed. Protocol protection is controlled by `emptyTurnGuard` (default on): empty visible answers and known REA/DSML/thinking residue become `OPENDESIGN_EOT`; prose, including pending-action narration, keeps its successful finish. Scoped request-error recovery retries EOT without an attempt limit using cancellable backoff and durable retry events; unrelated errors keep the host policy. Missing stream terminal events before tool calls are retryable as `TRANSPORT` for monitored attempts and `claude-opus-5.5` Messages calls.
- Task completion is a separate `agent/turn-stopping` handshake controlled by `turnCompletionReview`, which defaults to off and also requires `emptyTurnGuard`. With it disabled, a finished response ends the turn with no extra model step, no review input and no tool registration; the settings page shows the switch and disables its continuation limits. When enabled, register `opendesign_finish_turn` only in the Agent being reviewed, remove it with its turn/monitor lifetime, and retain original messages and executed tools. Accept declarations only after authoritative success and a successful durable root tool result; failed or blocked PTC envelopes cannot conclude a review. Evidence references must name observed successful results; this validates references, not full semantic task completion. Plain answers may require one extra review step. No arbitrary acceptance commands or second-model evaluator run automatically.
- Session `user/message` data is the UserMessage itself, unlike the wrapped assistant events. Match owned steering by message identity, turn and checkpoint; only human-source input supersedes an active review, not runtime-context refreshes or background notices.
- Bound appended review steps per turn and stop after repeated lack of new successful tool results; repeated text or identical tool results do not reset the fuse. Existing unfinished Goals own their lifecycle; running/stopping owned jobs and running local descendants imply waiting. Preserve cancellation, truncation, native concluding tools and fresh input. Diagnostics distinguish protocol intercepts, request retries, review checks and appended steps, expose fixed reasons rather than model output, and reset on plugin reload. See [monitor design](docs/empty-turn-evidence.md).
- Manual quota refresh bypasses cached data but shares an in-flight operation. Automatic failed reads back off from 5 to 60 seconds and stop after six consecutive failures; manual refresh or a relevant configuration change starts a new sequence.
- Unreadable image bytes fall back to a named placeholder; cancellation still terminates the request.

## Implementation ownership

- `src/config.ts`: validated, volatile configuration; `src/model-settings.ts`: per-model validation and capability/capacity overrides, field validation and composition for `contextTier` and the legacy `contextWindow` (the two are never both set); `src/image-budget.ts`: shared request-image budget bounds.
- `src/context-budget.ts`: the shared pure policy module for the context window — the three tiers (id, label, tokens), the effective working window (the selected tier capped by the known reference), and the legacy custom-window rule (a saved number keeps its own value and is never read as a tier).
- `src/schema-serialization.ts`: transform callbacks that survive repeated Host/browser serialization; `src/reasoning.ts`: shared model/protocol effort intersection.
- `src/claude-capabilities.ts`, `src/claude-parameters.ts`: version-scoped Claude sampling policy, shared by settings and request validation.
- `src/replay-key.ts`: lazy credential-service binding secret for signed thinking replay; use a process-local fallback only when the service is unavailable.
- `src/index.ts`: host service, credential references, quota/model refresh lifetimes, and provider registration.
- `src/remote.ts`: explicit JSON allowlists for the browser interface. Update them whenever a visible field is added.
- `src/quota.ts`, `src/desktop-quota.ts`: quota request/normalization; keep source and unit semantics explicit.
- `src/login.ts`, `src/device-auth.ts`: device authorization lifecycle, strict public-link validation, bounded requests and polling.
- `src/browser-open.ts`: the one temporary activation window. Single instance, bounded launch steps, closed on failure and on plugin disposal. Never touches an existing browser profile.
- `src/model-discovery.ts`: bounded OpenAI model discovery; no inference-protocol branching.
- `src/model-catalog-snapshot.ts`: the persisted gateway catalog snapshot — an untrusted-input validator that also serves as the `modelCatalog` Schemastery transform, kept closure-free for fresh-realm rehydration and aligned with the status transport's field limits.
- `src/eot-recovery.ts`: scoped EOT recovery at the Agent request-error boundary; never replays tools or changes unrelated retry policies.
- `src/turn-monitor.ts`, `src/turn-monitor-status.ts`: Agent-scoped completion handshake, bounded continuation, execution/durable-result confirmation and credential-free settings diagnostics.
- `src/pricing.ts`: bounded, credential-free public website pricing reader; retain original tier labels and reject incompatible price units/currencies.
- `src/adapter.ts`, `src/protocols/`: snapshot a call's configuration, translate requests and streams, enforce model enablement, and derive the automatic output reservation from the effective context window.
- `src/client.ts`: settings interactions and DSH semantic-theme styling, including the mutually exclusive context-tier control. It mounts both tier entry points and declares the client UI slot requirements they need. Form values must drive real host behavior.
- `src/client-context-quick.ts`: the chat-side context quick control — the per-session model directory it reads, the tier popover it renders, and the immediate save it requests through the shared coordinator.
- `src/client-config-writes.ts`: the shared configuration write coordinator for both tier entry points — per-field serialization, the pending overlay, and the model-settings field diff rebased onto the host's current map.
- `scripts/generate-remote.mjs`: generate the restricted Remote table from annotated host methods. Generated files are rebuilt, not edited by hand.

## Design and maintenance

See [usage](docs/usage.md), [quota evidence](docs/quota-evidence.md), and [UI design](docs/ui-design.md). The dependency and Core compatibility baseline is declared in `package.json`; consult its installed types instead of an unrelated DSH checkout.

Keep API keys and console credentials in the host credential service or environment references. Browser state and ordinary settings contain no credential values. The opened page is untrusted input: the plugin never types into it, clicks in it, or reads from it. All network readers need cancellation, size/time bounds, and safe errors. Model capabilities come from evidence or explicit user overrides, not guesses from vendor names.

Preserve MIT notices in `LICENSE` and `THIRD_PARTY_NOTICES.md`. Source changes do not automatically install, publish, or restart a host.

## Model catalog maintenance: evidence lookup

1. Check the [official model directory](https://corouter.open-design.ai/models/), [pricing cards](https://corouter.open-design.ai/zh/), and actual model detail pages. Core / Design Plan is the included pool; Plan / 套餐模型 is the paid pool. A missing detail route can return the homepage with HTTP 200: verify the page content, not just status. Keep media-only models out of the chat catalog.
2. For new IDs, query the official OpenAI-compatible `GET https://amr-link.open-design.ai/v1/models` with an authorized runtime/API credential, or use the desktop-bundled CLI below. A listing proves the service advertises an ID, not successful inference or subscription coverage. `metadata.cost` (`low` / `high`) and `capability` are hints, not entitlement or context/output-limit evidence. Do not classify by model size/name alone.
3. Locate the installed Open Design application and its own `resources/open-design/bin/vela.exe` (Windows layout observed in 0.26.1); verify the current executable and `--help` before reuse. Do not assume an unrelated PATH CLI or hard-code a maintainer's installation path. Run only read-only queries using the existing authorized login:

   ```text
   vela model list --all --format json
   vela team-projects list
   vela billing preflight --workspace-id <verified-workspace-id> --model <exact-model-id> --format json
   ```

   Obtain the intended workspace ID from the structured workspace result, keep it local, and use the same workspace for all comparisons. Probe one known Core model as a control, then each candidate. Do not infer a default team workspace from an unscoped catalog. Bound subprocess duration/output; parse locally and output only model IDs and necessary classification fields, not raw account/project data or credentials.
4. Inspect `codingPlan.eligible`, `modelCovered`, and `funding` together. A covered, eligible model reporting `funding: coding_plan` is positive evidence for the included channel in that workspace. `modelCovered: false` with `funding: wallet` supports paid routing there. Wallet funding alone can reflect exhausted/unavailable quota; it does not independently establish that a model is never covered. Missing/failed preflight means unknown. Record observation date and scope, never an account/workspace identifier; preflight is advisory and does not reserve quota or guarantee a run.
5. Check [official OpenDesign source](https://github.com/nexu-io/open-design) when interpreting results. Relevant paths: `apps/daemon/src/runtimes/amr-model-cache.ts` (remote catalog vs preset), `apps/daemon/src/runtimes/models.ts` (model resolution), `apps/web/src/runtime/amr-unlimited-models.ts` (tier labels are not coverage), and `specs/current/coding-plan-client-billing.md` (per-model preflight authority). Resolve the current revision and cite the inspected commit in [model evidence](docs/client-evidence.md). Static presets do not establish current entitlement.
6. Update [catalog](src/catalog.ts), [model evidence](docs/client-evidence.md), and focused catalog/discovery/provider/loader tests together. Keep unverified capability fields absent; do not copy a neighboring model's limits or infer support from a vendor name. Preserve Provider IDs and saved model settings. Run the verification below, including offline UI, and report live catalog/preflight checks separately from inference or installed-host verification.

## Verification

Run the relevant focused tests while developing, then `npm run check` and `npm run test:ui` for changes to these surfaces. The browser fixture is offline and must exercise settings persistence, model enablement/parameters, protocol selection, quota timing, and the per-session context quick control, including shared defaults, pending/rollback, model changes during saves, native popover toggling, keyboard focus, narrow viewports, light/dark/forced-color themes, and disposal of both surfaces. Loader tests verify the built package and generated Remote registrations. Test assertions must follow the intended behavior above; passing static or mocked checks alone is not evidence of live account integration.
